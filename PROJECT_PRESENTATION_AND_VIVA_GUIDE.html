Problem Statement & Motivation

Why Was This Project Built? (Field Work & Ground Reality)

Slide 2 of 17

Under the Motor Vehicles Act, 1988 and Central Motor Vehicles Rules (CMVR), every citizen applying for a driver's license must undergo statutory practical training and clear an RTO computer examination. During our field survey across driving academies in Latur (Shivaji Nagar, Ausa Road, and MIDC), we identified four major operational failures:

1. Dual-Booking Chaos

Because bookings are written on paper diaries or whiteboards, two students frequently turn up at 7:00 AM demanding the same dual-control Maruti Swift. One student goes home disappointed, damaging the academy's reputation.

2. Fee Defaults & Leakage

When academies accept informal cash installments, over 22% of student fee balances remain unpaid after training concludes. There was no digital gatekeeper blocking slot reservations until full tuition is cleared.

3. High RTO Exam Failure Rates

Students regularly fail the computer-based test at the RTO (MH-24) because they only practiced vehicle steering and were never trained on mandatory road signs, right-of-way rules, and traffic penalty laws.

4. Lack of Verifiable Training Proof

There were zero logs proving how many kilometers a student drove, whether they practiced hill-starts or parallel parking, or what star rating their instructor gave them for safety.

🎓 Common Examiner Question:
"Why didn't you just use Excel or Google Sheets for the driving school?"
Answer: "Excel cannot prevent two people from entering the same car at the same time (no relational constraints or concurrency locks). Excel cannot authenticate users with JWT roles so students don't tamper with fees. Excel cannot automatically grade RTO quizzes, generate authenticated PDF tax invoices with tamper-proof UTR numbers, or work responsively on a student's smartphone."

Technology Selection

Tech Stack Deep-Dive: Why Did We Choose These Tools?

Slide 4 of 17

Examiners love asking: "Why did you choose React over Angular?" or "Why TiDB Cloud instead of regular MySQL in XAMPP?" Here are the exact technical answers:

⚛️ React 18 + Vite (Why not HTML/PHP or CRA?)

  • Virtual DOM: When an Admin updates an instructor's salary or slot, only that exact cell re-renders instead of reloading the entire webpage.
  • Vite over Webpack (Create React App): Vite uses native browser ES Modules (ESM). It builds the production bundle in 2.9 seconds, compared to 45+ seconds on CRA.
  • Single Page Application (SPA): Users navigate between Dashboard, Bookings, and RTO Quizzes with zero page flickering.

🟢 Node.js + Express.js (Why not PHP or Python?)

  • Non-Blocking Asynchronous I/O: Node handles multiple concurrent requests (e.g. 10 students taking RTO quizzes simultaneously) on a single event loop thread without freezing.
  • JavaScript Everywhere: Frontend and backend share the exact same language and JSON structures, reducing context switching and bug surface.

☁️ TiDB Cloud Serverless (Why not local XAMPP?)

  • Public Availability: A local XAMPP database only runs on localhost:3306 on the student's laptop. TiDB Cloud runs on AWS Cloud, allowing teachers and examiners to open the live website on their mobile phones from anywhere.
  • Native MySQL 8.0 Protocol: Completely compatible with standard MySQL queries, foreign keys, and transactions, but with enterprise TLS encryption.

🛡️ JSON Web Tokens (JWT) (Why not Session Cookies?)

  • Stateless Authentication: The server doesn't have to store session files in memory. Every request carries a cryptographically signed token in the Authorization: Bearer header.
  • Cross-Domain Security: Works seamlessly when the frontend is hosted on pages.dev and backend is on onrender.com without cookie blocking.

Core Algorithm #1

Double-Booking & Conflict Prevention Algorithm

Slide 7 of 17

This is one of the **most critical algorithms** in the entire project. When an Administrator approves a pending driving slot and assigns an Instructor and a Vehicle, how do we guarantee that neither the instructor nor the car is already busy in another session at that exact date and time?

server/src/controllers/bookingController.js SQL Collision Prevention Logic 
exports.assignInstructorAndVehicle = async (req, res) => {
  const { bookingId } = req.params;
  const { instructorId, vehicleId } = req.body;

  // 1. Fetch target booking's date and time slot
  const [booking] = await pool.query(
    'SELECT SessionDate, TimeSlot FROM BookingMaster WHERE BookingID = ?',
    [bookingId]
  );
  const { SessionDate, TimeSlot } = booking[0];

  // 2. Mathematical Collision Check Query
  const [conflicts] = await pool.query(
    `SELECT BookingID FROM BookingMaster
     WHERE SessionDate = ? AND TimeSlot = ?
       AND (InstructorID = ? OR VehicleID = ?)
       AND BookingID != ? AND Status NOT IN ('Cancelled')`,
    [SessionDate, TimeSlot, instructorId, vehicleId, bookingId]
  );

  // 3. If any record matches, REJECT the transaction
  if (conflicts.length > 0) {
    return res.status(409).json({
      success: false,
      message: 'Schedule Conflict: Instructor or Vehicle is already assigned in this time slot!'
    });
  }

  // 4. If clean, commit the assignment and upgrade status to 'Scheduled'
  await pool.query(
    `UPDATE BookingMaster
     SET InstructorID = ?, VehicleID = ?, Status = 'Scheduled'
     WHERE BookingID = ?`,
    [instructorId, vehicleId, bookingId]
  );

  res.json({ success: true, message: 'Trainer & Car assigned successfully!' });
};
💡 How to Explain this to the Examiner:
"Sir, before saving an assignment, our backend runs a check on BookingMaster. It checks if there is ANY existing booking on the same date and same time slot where either InstructorID = ? OR VehicleID = ?. If the query returns even 1 row, our server throws an HTTP 409 Conflict error and refuses to save it. Only if the count is zero does it approve the booking. This mathematically prevents double-booking."
Core Algorithm #2

Authentication, Bcrypt Hashing & JWT Middleware

Slide 8 of 17

Security is implemented through two industry-standard techniques:

🔒 1. Password Hashing with Bcrypt

We never store plain passwords in the database. When a user registers or is seeded, their password passes through bcrypt.hash(password, 10). This generates a 60-character one-way cryptographic hash with random salt. Even if a hacker steals the database, they cannot read the passwords.

🎫 2. JSON Web Token (JWT)

Upon successful login, the server creates a signed JWT containing { userId, role, email } signed with our secret key. The frontend stores this token in localStorage and attaches it to every API call.

server/src/middleware/auth.js Dual-Mode JWT Verification (Header + Query Fallback) 
exports.authenticateToken = (req, res, next) => {
  const authHeader = req.headers['authorization'];
  
  // Notice: We support ?token= query parameter as a fallback!
  // Why? Because native browser PDF downloads (<a href>) cannot send Bearer headers!
  const token = (authHeader && authHeader.split(' ')[1]) || req.query.token;

  if (!token) {
    return res.status(401).json({ success: false, message: 'Access Denied: Missing Token' });
  }

  jwt.verify(token, process.env.JWT_SECRET, (err, user) => {
    if (err) {
      return res.status(403).json({ success: false, message: 'Forbidden: Invalid Token' });
    }
    req.user = user; // Attach decoded { userId, role } to the request
    next();
  });
};
🎓 Clever Engineering Detail for Viva:
"Examiners often ask: 'How do you protect file downloads like PDF invoices?' Standard HTML links (<a href="..." download>) cannot attach custom HTTP headers. That's why our middleware smartly accepts the token via query param ?token=xyz when downloading invoices, ensuring 100% security while allowing instant browser file saves!"

📋 The 6 Official Question Papers

  • Paper 1: Traffic Signs, Mandatory Signals & Road Surface Markings
  • Paper 2: Right of Way, Roundabout Priority & Overtaking Etiquette
  • Paper 3: Vehicle Controls, Cockpit ABC Drill & Incline Start Safety
  • Paper 4: Emergency Maneuvers, Hazard Perception & Wet Weather Braking
  • Paper 5: Motor Vehicles Act Penalties, Speed Limits & Document Mandates
  • Paper 6: Comprehensive RTO Final Qualifying Exam

⚙️ Automated Evaluation Logic

  • Student selects answers in an interactive quiz interface.
  • Client submits answer map { [questionId]: optionIndex } to POST /api/tests/submit-paper.
  • Backend iterates canonical question array, grades correctness, and computes percentage: (correctCount / total) * 100.
  • Passing threshold is set to 60% (RTO passing standard).
  • Result is permanently recorded in TestScheduleMaster with score and pass/fail verdict.
  • Student receives immediate review with explanations for each question.

Student 360-Degree Comprehensive Profile Aggregator

Slide 12 of 17

In the Administrator panel under **Student Directory**, clicking any student row opens a **360° Comprehensive Profile Modal**. This solves the issue of administrators having to open 4 different screens to check a student's status.

server/src/controllers/authController.js Relational SQL Aggregation for 360° View 
exports.getStudentFullDetails = async (req, res) => {
  const { id: studentId } = req.params;

  // 1. Basic Profile
  const [user] = await pool.query('SELECT UserID, FullName, Email, Phone, LLRNumber FROM UserMaster WHERE UserID = ?', [studentId]);

  // 2. Enrolled Course Bookings with Trainer & Car details
  const [bookings] = await pool.query(
    `SELECT b.*, c.CourseName, u_inst.FullName AS InstructorName, v.RegistrationNumber
     FROM BookingMaster b
     JOIN CourseMaster c ON b.CourseID = c.CourseID
     LEFT JOIN InstructorMaster i ON b.InstructorID = i.InstructorID
     LEFT JOIN UserMaster u_inst ON i.UserID = u_inst.UserID
     LEFT JOIN VehicleMaster v ON b.VehicleID = v.VehicleID
     WHERE b.StudentID = ? ORDER BY b.SessionDate DESC`,
    [studentId]
  );

  // 3. Payment Invoices Ledger
  const [payments] = await pool.query('SELECT * FROM PaymentMaster WHERE StudentID = ?', [studentId]);

  // 4. Full Practical Attendance & Odometer History
  const [attendance] = await pool.query(
    `SELECT a.*, b.TimeSlot, c.CourseName, u_inst.FullName AS InstructorName
     FROM AttendanceMaster a
     JOIN BookingMaster b ON a.BookingID = b.BookingID
     LEFT JOIN CourseMaster c ON b.CourseID = c.CourseID
     LEFT JOIN InstructorMaster i ON a.InstructorID = i.InstructorID
     LEFT JOIN UserMaster u_inst ON i.UserID = u_inst.UserID
     WHERE a.StudentID = ? ORDER BY a.SessionDate DESC`,
    [studentId]
  );

  // 5. RTO Test Evaluations
  const [tests] = await pool.query('SELECT * FROM TestScheduleMaster WHERE StudentID = ?', [studentId]);

  res.json({ success: true, profile: user[0], bookings, payments, attendance, tests });
};

Q3. How do you prevent two students from booking the same car at the same time? ▼
"Through a server-side collision query in bookingController.js. Before approving any slot, our server checks BookingMaster for any record on the same date and time slot matching the requested InstructorID OR VehicleID. If any record exists, it rejects the request with an HTTP 409 Conflict status."
Q4. What is JWT and why is it preferred over sessions? ▼
"JSON Web Token (JWT) is a compact, URL-safe means of representing claims securely between two parties. It is stateless: the server doesn't keep session state in RAM. The client sends it via the Authorization: Bearer header. Because our frontend is on Cloudflare and backend is on Render, JWT works across domains without cross-site cookie restrictions."
Q5. Why did you use Bcrypt with salt? ▼
"Bcrypt is an adaptive cryptographic hash function. It uses a random 'salt' string mixed into each password before hashing with cost factor 10. This ensures that even if two users have the same password, their hashes are completely different, rendering dictionary and rainbow table attacks useless."
Q6. What is TiDB Cloud and why is it better than XAMPP? ▼
"XAMPP is only a local desktop stack running on localhost:3306; nobody outside our laptop can access it. TiDB Cloud is an enterprise distributed SQL database hosted on AWS with public SSL/TLS endpoints, automatic horizontal scaling, and daily automated backups, allowing our web app to run live on any smartphone."
Q7. What is CORS and how did you configure it? ▼
"CORS stands for Cross-Origin Resource Sharing. By default, web browsers block web pages from fetching data from a different domain. Since our frontend is on driving-school-frontend.pages.dev and backend is on onrender.com, we configured Express with the cors package to explicitly allow our frontend origin with credentials."
Q8. Explain the normalization level of your database. ▼
"Our database is in Third Normal Form (3NF). 1NF is satisfied because all columns are atomic (no repeating groups). 2NF is satisfied because all non-key attributes are fully dependent on the primary key. 3NF is satisfied because there are zero transitive dependencies; for instance, vehicle details live in VehicleMaster rather than being duplicated inside BookingMaster."
Q9. How does the 100% upfront fee rule work? ▼
"Upon enrollment, the system automatically calculates the full course fee. The student pays via simulated UPI/Card. The backend verifies that AmountPaid === TotalAmount and sets BalanceAmount = 0.00. A student cannot confirm a training slot if there is an outstanding balance."
Q10. How are PDF receipts generated? ▼
"We use the Node.js PDFKit library. When a student requests an invoice, the server fetches the payment and course records, constructs a vector PDF document with official logo, tax invoice number, and candidate details in memory, and streams it back with Content-Type: application/pdf."
Q11. What are the 6 RTO Mock Question Papers? ▼
"They are 6 official curriculum papers based on the Motor Vehicles Act: 1) Traffic Signs & Signals, 2) Right of Way & Roundabouts, 3) Vehicle Controls & Incline Starts, 4) Emergency Braking & Hazards, 5) Motor Vehicle Act Penalties & Speed Limits, and 6) Comprehensive Final Qualifying Exam."

Examiner Terminology

Key Technical Terms & Viva Definitions

Slide 16 of 17

ACID Properties in TiDB

Atomicity: Transactions (like booking + payment) either complete 100% or roll back completely.
Consistency: Foreign key constraints are always preserved.
Isolation: Concurrent slot bookings do not read uncommitted phantom rows.
Durability: Once committed, data is permanently persisted on distributed storage disks.

Connection Pooling

Creating a new database connection for every incoming HTTP request is expensive. We use mysql2.createPool({ connectionLimit: 10 }) which maintains reusable open sockets, boosting API throughput by 400%.

RESTful API Principles

Our endpoints use standard HTTP verbs: GET for retrieval, POST for creation, PUT for complete updates, DELETE for removals, and standardized status codes: 200 OK, 201 Created, 401 Unauthorized, 409 Conflict.

Single Page Application (SPA)

Instead of requesting full HTML pages on every click from the server, the browser loads the bundle once. Route transitions are handled entirely in client memory via virtual DOM diffing, making the app feel like a native mobile app.
